# EdgeDeck — панель маршрутизации сервера

> Дизайн-документ. Версия 1, 19 августа 2026.
> Сервер: `150.136.40.217` (oracle-3), каталог проекта на машине: `D:\CLOUDE\edgedeck`.
> Наследник `~/edge` (Caddy) — не выбрасываем, а обрастаем панелью вокруг него.

---

## 0. Одним абзацем

Панель в браузере, где видно **все домены и порты сервера в одном списке** и можно
привязать домен (или путь) к чему угодно, что на этом сервере крутится: контейнер,
процесс вне докера, папка со статикой, другой сервер. Панель сама находит кандидатов,
сама проверяет, что цель отвечает, **до** того как что-то применит, и умеет откатиться,
если стало хуже. Работает в докере, управляет только тем сервером, где стоит, входим по
паролю.

Ключевая идея, из которой всё вытекает: **источник истины — файлы, панель — удобный
редактор поверх них.** Всё, что делает панель, можно повторить руками по SSH. Панель
может умереть — сайты продолжат работать.

## 2. Каталог грабель — опыт двух старых серверов

Это главная часть документа. Каждый пункт — реально случившееся, и из каждого следует
требование к панели. Отмечено, что проверено сегодня живьём.

### 2.1. Монолитный конфиг, который страшно править

На s1 `nginx.conf` — 10 КБ в одном файле, рядом **11 файлов** `nginx.conf.bak-*`
(`bak-predeploy`, `bak-hardening-20260731-142401`, `bak-csp-084458`, …). Бэкапы появились
не от аккуратности, а от страха: одна опечатка — и падают все пять доменов сразу.

→ **Требование:** один домен = один файл. Изменение одного сайта физически не может
сломать другой. История правок ведётся автоматически (git в каталоге конфигов), руками
`.bak` создавать не нужно и не принято.

### 2.2. 502 после пересоздания контейнера

nginx резолвит имена апстримов один раз при старте. Пересобрал приложение → новый IP →
502 до перезагрузки nginx. Лечится трюком, который в конфиге s1 стоит первой строкой:

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;
...
set $jarvis_upstream http://jarvis:4000;   # через переменную — иначе резолв на старте
proxy_pass $jarvis_upstream;
```

Caddy так не умирает (резолвит на каждый запрос), но грабля остаётся в другом виде:
контейнер может быть просто выключен.

→ **Требование:** у каждого маршрута есть живой статус («цель отвечает / не отвечает /
цели вообще нет»), и он виден на главном экране, а не выясняется по жалобе.

### 2.3. Прокси должен быть в сети приложения — самая частая причина 502

На s1 `edge_proxy` подключён к **четырём** сетям: `root_website_hubnet`, `edge-proxy_edgenet`,
`twcrm_default`, `apiary_net`. В `docker-compose.yml` про apiary даже приписка стоит:
«панель Apiary живёт в своей сети — без неё прокси даёт 502».

Каждый новый сайт = правка чужого compose-файла или compose прокси. Забыл — 502, и
причина не очевидна: конфиг валиден, контейнер жив, домен резолвится.

→ **Требование:** панель видит, в каких сетях цель, и если она не в `edge` — **одной
кнопкой подключает** (`docker network connect`), не трогая ничей `docker-compose.yml`.
Это единственная операция записи в докер, которую панель себе позволяет.
Плюс предупреждение: подключение сетью не выживет `docker compose up --force-recreate`
без правки compose — панель показывает готовый кусок yaml, чтобы закрепить.

### 2.4. Сервисы, опубликованные на 127.0.0.1, недостижимы из контейнера

На s1 так живут `dozzle` (127.0.0.1:8087), `cadvisor` (127.0.0.1:8081), `apiary-web`
(127.0.0.1:8100), `apiary-mc262` (25567/25576). Логика правильная — не светить наружу.
Но из другого контейнера туда не попасть: `127.0.0.1` внутри контейнера — это он сам.
Именно поэтому dozzle пришлось дополнительно завести в `root_website_hubnet`.

**Проверено сегодня на s3:** контейнер → `host.docker.internal:19999` (порт опубликован
как `127.0.0.1:19999`) = отказ соединения, при том что с хоста тот же порт отдаёт 200.

→ **Требование:** тип цели «контейнер» всегда маршрутизируется по docker-сети
(`имя:внутренний_порт`), а не через опубликованный порт. Публикация на хосте — вообще
не наше дело; панель показывает её только как информацию «этот порт занят».

### 2.5. Не всё живёт в докере

На s1 вне докера: `pufferpanel` (:8080 и :5657), `java25` — майнкрафт (:25566, RCON
:25575), `node_exporter` (:9100), `vmagent` (:8429). На s2 то же плюс `java` (:25577).

→ **Требование:** тип цели «процесс на хосте». Панель находит такие порты сама (читает
`/proc` хоста, как это делает node_exporter) и показывает, каким процессом порт занят.

### 2.6. 🔴 На s3 процесс вне докера недостижим, и ufw тут не поможет

Самое неожиданное из сегодняшнего. Порядок цепочки INPUT:

```
s3:  ... -A INPUT -j REJECT --reject-with icmp-host-prohibited   ← Oracle
     -A INPUT -j ufw-before-input                                ← ufw ПОСЛЕ него

s1:  -A INPUT -j ufw-before-input                                ← ufw ПЕРВЫМ
     ...
s2:  -A INPUT -j ufw-before-input                                ← ufw ПЕРВЫМ
```

На s1/s2 правила ufw работают: `pufferpanel:8080` отдаёт 200 из интернета (проверено).
На s3 стоковое правило Oracle стоит **выше** ufw-цепочек, поэтому:

* любой ufw-allow, кроме 22, — мёртвый код;
* сайты на 80/443 работают только потому, что это docker-порты: DNAT уводит их в
  FORWARD, минуя INPUT (проверено: контейнер → `172.17.0.1:80` = 200);
* процесс, поднятый на s3 **не** в докере, будет недоступен ни снаружи, ни из контейнера
  прокси. Проверено: контейнер → `172.17.0.1:111` (rpcbind на хосте) = отказ, и
  добавление `ufw allow from 172.17.0.0/16` ничего не меняет.

→ **Требование:** в установщике панели — разовая проверка порядка цепочки с явным
предложением починить (`iptables -I INPUT` до REJECT + сохранение правил) и объяснением,
что именно изменится. Правки фаервола пользователь одобрил не автоматизировать, поэтому
панель показывает готовую команду, а не выполняет её. Тип цели «процесс на хосте» на s3
до этой починки помечается как «не заработает, вот почему».

### 2.7. Сертификаты продлеваются вручную, и об этом никто не знает

В кроне s1 висит:

```
0 3,15 * * * docker compose exec reverse-proxy certbot renew --quiet
```

**Проверено сегодня:** `service "reverse-proxy" is not running` — контейнер давно
называется `edge_proxy`. То есть **продление не работает уже месяцы**, а сроки такие:

| домен | действителен до |
|---|---|
| maxsolch.com | 4 октября 2026 |
| maxsolkh.shop | 8 октября 2026 |
| tgdesk.tech | 15 октября 2026 |
| bots.bogun.site | 13 ноября 2026 |
| bogun.site | 15 ноября 2026 |

Молчаливо сломанная автоматизация хуже её отсутствия.

→ **Требование:** (а) TLS полностью на Caddy, никакого certbot; (б) на главном экране
дата истечения каждого сертификата с цветом; (в) панель проверяет **сама себя**: если
задача продления не отработала — это видно как ошибка, а не как тишина.

### 2.8. Let's Encrypt наказывает за спешку

Лимит — 5 повторных выпусков одного набора имён в неделю, плюс 5 неудачных проверок в
час. Достаточно нажать «выпустить» на домене, у которого A-запись ещё не переехала, пять
раз — и домен заперт на неделю. В `docker-compose.yml` на s3 из-за этого стоит
предупреждение никогда не удалять том `caddy_data`.

→ **Требование:** перед включением TLS панель делает **предполётную проверку**: домен
резолвится → в A-записи именно IP этого сервера → порт 80 снаружи доходит до нас.
Не сошлось — кнопка «выпустить» неактивна с объяснением, а не с ошибкой после факта.
Том с сертификатами в интерфейсе помечен как неудаляемый.

### 2.9. Домен, у которого TLS живёт не здесь

`maxsolkh.shop` на s1: TLS терминирует свой Caddy на портах 666/667, а edge держит
только `/.well-known/acme-challenge/` и отдаёт 404 на всё остальное.

→ **Требование:** маршрут может быть не только «прокси» и «статика», но и:
«только редирект», «только ACME», «заглушка/404». Четыре типа, а не два.

### 2.10. Один домен — несколько маршрутов по путям

На `bogun.site`: `/logs/` → dozzle, `/vault/` → vaultwarden, `/` → jarvis. Причём
`/logs/` закрыт подзапросом авторизации к панели:

```nginx
location = /_authcheck { internal; proxy_pass http://jarvis:4000/api/authcheck; }
location /logs/ { auth_request /_authcheck; ... }
```

→ **Требование:** единица управления — **маршрут (домен + путь)**, а не домен.
«Требовать вход» — галочка у маршрута (в Caddy это `forward_auth`), а не ручная сборка
из трёх директив.

### 2.11. Заголовки: два CSP ломают сайт

Прямо в конфиге s1 записан вывод, добытый болью:

> `add_header` не заменяет заголовок апстрима, а добавляет второй — браузер получил бы
> два CSP и применил их пересечение, что при малейшем расхождении ломает панель.

Поэтому там `proxy_hide_header Content-Security-Policy;` и комментарий: если управлять
CSP с edge — сначала убрать её из конфига приложения.

→ **Требование:** заголовки безопасности — набор понятных тумблеров, и панель
**сначала смотрит, что уже отдаёт цель**. Апстрим уже присылает CSP → тумблер
показывает: «цель уже ставит этот заголовок; включить — значит заменить (скрыть её)».
Двойной заголовок панель выставить не даёт.

### 2.12. Запрет пути, который выстрелил в себя

Там же: `/api/metrics` закрыт 404-м (телеметрия наружу не нужна). А `/api/system/info`
закрывать было **нельзя** — его читает сам фронтенд панели через тот же edge, и правило
било по пользователю. В конфиге теперь абзац с объяснением, чтобы не повторили.

→ **Требование:** «закрыть путь» — правило с обязательным пробным запросом до
применения (что вернётся до и после), и с оговоркой, что запрет действует и на браузер
пользователя.

### 2.13. WebSocket, таймауты, размеры

Из живого конфига: `proxy_read_timeout 3600s` и `proxy_buffering off` для WebSocket
панели Apiary (события + камера); `client_max_body_size 128M` для Vaultwarden (иначе
413 на вложениях); `proxy_read_timeout 1h` для логов dozzle.

→ **Требование:** у маршрута поля «максимальный размер загрузки» и «таймаут ответа»
с человеческими подписями.

Тумблера «долгие соединения (WebSocket)» в итоге **нет**, и это не упущение:
Caddy проксирует Upgrade сам и по умолчанию не ставит таймаут на чтение. Половина
боли из этого пункта была свойством nginx, а не задачи. Поэтому таймаут в панели —
это возможность его **ограничить**, а не разрешить.

### 2.14. HSTS — билет в одну сторону

В `snippets/common.caddy` на s3 уже написано правильно: HSTS вынесен отдельно и по
умолчанию выключен, потому что браузер запомнит его на год и при поломке TLS сайт станет
недоступен, а откатить нельзя.

→ **Требование:** HSTS — отдельный тумблер, выключен, с предупреждением при включении
и без возможности «включить всем сразу».

### 2.15. Домен без настроек не должен попадать на случайный сайт

Отдельный файл `_default.caddy` существует ровно потому, что иначе Caddy отдаст первый
сайт по алфавиту — классический источник «почему на моём новом домене чужой сайт».
На s1 та же роль у `default_server`.

→ **Требование:** обработчик по умолчанию неудаляем — и это **сама панель** (см. §9.0).
Домен, у которого ещё нет маршрута, показывает панель; как только маршрут создан — уходит
на сайт. В панели видно, какие домены сейчас приходят на дефолт.

### 2.16. ufw создаёт ложное чувство защиты

На s1 в ufw **36 правил**, включая 8080, 9000, 8888, 7777. При этом ufw в принципе
не фильтрует docker-порты: публикация идёт через DNAT в FORWARD, а ufw смотрит INPUT.
Единственное место, где docker-порт можно ограничить, — цепочка `DOCKER-USER`, и на s1
она **пустая**. Наружу поэтому смотрят: `3341` (MySQL tgshop), `9002/9003` (MinIO),
`8090/8091` (внутренние gateway), `8000/8082/9443` (Portainer). На s2 отдельно
`2375` — docker-socket-proxy. На s3 в `DOCKER-USER` уже есть правильная пара правил
для 9001 (`/opt/docker-acl`).

→ **Требование:** экран «Порты» показывает честную картину по трём слоям:
кто слушает → есть ли правило в `DOCKER-USER` → есть ли правило в ufw → **вывод одной
строкой: «видно из интернета» / «видно только с адресов …» / «только локально»**.
Проверка снаружи опциональна (панель может попросить второй сервер постучаться).
Менять фаервол панель не будет — выдаёт готовые команды.

### 2.17. Порт 443 не всегда наш

На s2 `0.0.0.0:443` держит **xray** (VLESS/Reality), а не веб-прокси. Любая логика
«443 = наш HTTPS» там неверна.

→ **Требование:** панель при установке проверяет, кто занимает 80/443, и не пытается
воевать. На будущем L4-этапе появляется сценарий «делить 443 по SNI».

### 2.18. Каталоги проектов лежат вразнобой

Compose-проекты на s1: `~/APIARY`, `~/APIARY/testserver`, `~/edge-proxy`, `~/JARVIS`,
`~/TELEGRAM_BOTS/maxsolch-v2`, `~/MONITORING`, `~/PORTAINER`, `/opt/twcrm`, `~/VAULTWARDEN`.
Никакой единой структуры нет и не будет.

→ **Требование:** панель ничего не предполагает о расположении. Каталог проекта берётся
из docker-метки `com.docker.compose.project.working_dir` — и используется только чтобы
показать «где это лежит», для копирования пути.

### 2.19. Панель не должна быть единственным входом

16 августа s1 ушёл в спящий режим и пропал из сети — чинилось только через консоль
Oracle. Плюс агент Portainer на s2 висел на 9001 в интернете без секрета.

→ **Требование:** (а) панель не публикует свой порт на хосте вообще — только через
Caddy на домене; (б) всё состояние — обычные текстовые файлы, которые правятся по SSH,
если панель мертва; (в) панель не умеет запускать/удалять контейнеры, чтобы её взлом не
означал захват сервера.

### 2.20. Мелочь, которая укусит: логи и IPv6

Docker-логи на серверах не ротируются (отдельный пункт прошлого аудита). У s3 нет IPv6,
а конфиги s1 содержат `listen [::]:443`.

→ **Требование:** свои логи панель ротирует сама (как уже делает Caddy: `roll_size 10MiB`,
`roll_keep 5`), а в генерируемых конфигах IPv6-слушателей не появляется, пока на машине
нет IPv6.

### 2.21. 🔴 Правка файла, смонтированного в контейнер, ломает монтаж

Найдено при первой же установке. `~/edge/Caddyfile` смонтирован как **файл**:

```yaml
volumes:
  - ./Caddyfile:/etc/caddy/Caddyfile:ro
```

Docker привязывает такой монтаж к **иноду**. `sed -i` (как и любая запись «во
временный файл и `mv`» — то есть обычная практика атомарной записи!) создаёт
новый инод. Хост видит новую версию, а контейнер — навсегда старую. Ошибка при
этом получается совершенно не про то: Caddy жаловался на «on-demand TLS без
модуля разрешений», потому что читал старый конфиг без блока `on_demand_tls`.

→ **Требование:** файлы, смонтированные внутрь контейнеров, панель правит
**сохраняя инод** (открыть и усечь на месте), а не через `tmp` + `rename`. Это
прямо противоречит обычному «атомарная запись = tmp+rename», поэтому вынесено
в отдельное правило. И дополнительно панель сверяет `sha256` файла на хосте и
внутри контейнера — расхождение значит отвязавшийся монтаж, лечится
пересозданием контейнера.

### 2.22. Let's Encrypt не выдаёт сертификаты на IP-адреса

Заход по IP — обязательная часть сценария (§9.0), но:

```
HTTP 400 urn:ietf:params:acme:error:rejectedIdentifier
Error creating new order :: Default profile does not permit IP address identifiers
```

→ **Требование:** для IP — свой самоподписанный сертификат на 10 лет, который
кладёт установщик. Не `tls internal`: внутренний CA Caddy в паре с on-demand на
том же порту приводил к **висящему рукопожатию**, а не к понятной ошибке.

### 2.23. Браузеры не отправляют SNI для IP-адресов

Из того же корня. Соединение без SNI не подходит ни под одну политику с
конкретным именем и попадает в catch-all с on-demand, где имя пустое → зависание.
Лечится `default_sni <IP>` в глобальных опциях: он добавляет пустой SNI в
сопоставление политики и подставляет имя при выборе сертификата.

Тонкость: `default_sni` работает **только вместе с явным файлом сертификата**.
С `tls internal` он же затягивал IP в управление по ACME — то есть в §2.22.

### 2.24. Опции устаревают молча

`on_demand_tls { interval 2m; burst 5 }` из статей и старых конфигов в Caddy 2.11
уже ошибка: «the on_demand_tls 'interval' option is no longer supported». Значит
ограничение частоты выпуска — целиком наша забота (мы и так его делаем в панели).

→ **Требование:** установщик и генератор всегда прогоняют конфиг через
валидацию Caddy до применения, а не полагаются на то, что синтаксис не менялся.

### 2.25. `/proc/sys/kernel/hostname` в контейнере врёт даже через монтаж хоста

Панель монтирует `/proc` хоста, но это имя зависит от UTS-namespace, поэтому
чтение отдаёт имя контейнера (`cbb35d9c4f77` вместо `oracle-3`). А вот
`/host/proc/1/net/tcp` работает как ожидается — сетевые файлы читаются из
пространства процесса, чей каталог открыли.

→ **Требование:** имя сервера берём у Docker (`/info` → `Name`) через агента.

### 2.26. Имя процесса вне докера стоит слишком дорого

Порт хоста панель видит (`/host/proc/1/net/tcp`), а вот **кто его держит** — нет:
чтобы раскрыть инод сокета в процесс, надо читать `/host/proc/<pid>/fd`, а это
требует `pid: host` **и** `CAP_SYS_PTRACE`. То есть контейнер получил бы обзор
всех процессов сервера и право посылать им сигналы — ради подписи в списке.

→ **Решение:** не берём. Панель показывает номер порта, отметку «процесс на
хосте» и подсказку по известным номерам («похоже на SSH»), а для docker-портов
подставляет имя контейнера через агента — этого достаточно, чтобы принять решение
о маршруте. В интерфейсе прямо написано, почему имени нет: пользователь должен
видеть, что это выбор, а не поломка.

### 2.28. Редеплой контейнера отбирает сети, добавленные извне

`docker compose up -d --force-recreate` поднимает контейнер только с теми сетями,
которые перечислены в **его** compose-файле. Подключение к `edge`, сделанное
панелью через `docker network connect`, при этом теряется — и маршрут отдаёт 502
навсегда, пока кто-то не подключит сеть заново.

Проверено на живом сервере: после редеплоя у контейнера осталась только его
собственная сеть, сайт отдал 502.

→ **Требование:** панель раз в десять секунд сверяет, что контейнеры, на которые
есть маршруты, находятся в сети `edge`, и возвращает потерянные подключения сама.
Работает независимо от уведомлений — это условие работоспособности, а не отчёт.
Постоянное решение (строка `networks` в compose приложения) панель показывает
рядом с целью, но пока её нет, сайт не должен лежать. Проверено: после редеплоя
сайт возвращается сам за ~9 секунд, и всё это время посетитель видит внятную
страницу, а не «502 Bad Gateway».

### 2.27. `cap_drop: ALL` забирает у root право писать в чужой каталог

Контейнер, который читает правила фаервола, запущен максимально урезанным:
`cap_drop: ALL` плюс только `NET_ADMIN` и `NET_RAW`. И он молча не мог создать
файл в каталоге, принадлежащем `ubuntu`, — потому что вместе со всеми
capabilities root теряет `CAP_DAC_OVERRIDE`, то есть право обходить проверку
прав доступа. Внешне это выглядело как «сборщик работает, файла нет».

→ **Требование:** каталог для снимка принадлежит root (его создаёт установщик),
а сам сборщик проверяет право записи **при старте** и падает с объяснением.
Общее правило: если процесс должен что-то писать, право записи проверяется на
старте, а не в момент, когда данные понадобились.

## 3. Понятия

Пять сущностей, больше не нужно.

**Маршрут (Route)** — что панель создаёт. Домен + путь + куда + как.
`tgdesk.tech` `/` → контейнер `twcrm-frontend:80`.
Поля: домен, путь (по умолчанию `/`), тип, цель, тумблеры (WebSocket, размер загрузки,
таймаут, заголовки, HSTS, требовать вход, ACL по IP), статус, комментарий.

**Тип маршрута** — пять штук:

| тип | что делает | откуда взялось |
|---|---|---|
| `proxy` | проксирует на цель | основной случай |
| `static` | отдаёт папку | `www/домен/` |
| `redirect` | 301 на другой адрес | `www.` → без `www.` |
| `acme_only` | только `/.well-known/`, остальное 404 | `maxsolkh.shop` (§2.9) |
| `stub` | заглушка/404/«скоро откроется» | домен куплен, сайта нет |

**Цель (Target)** — куда именно:

| тип цели | адрес в конфиге | требует |
|---|---|---|
| контейнер | `имя:внутренний_порт` | контейнер в сети `edge` (§2.3) |
| процесс на хосте | `host.docker.internal:порт` | `extra_hosts: host-gateway` + порядок iptables (§2.6) |
| папка | `/var/www/домен` | файлы в `~/edge/www/` |
| внешний адрес | `https://другой-сервер:порт` | ничего |

**Сертификат** — домен, срок, кем выпущен, последняя попытка продления. Только чтение:
управляет Caddy, панель показывает и предупреждает.

**Порт** — запись реестра: номер, протокол, кто слушает (процесс или контейнер), на
каком интерфейсе, вывод о доступности снаружи (§2.16). Только чтение + подсказки.

**Изменение (Change)** — запись в истории: кто, когда, что, diff конфига, результат
применения, ссылка на откат. Единица аудита и единица отката.

## 4. Архитектура

Четыре контейнера, все в сети `edge`, наружу опубликованы только 80/443 у Caddy.

```
                    интернет :80 :443
                           │
                  ┌────────▼────────┐
                  │   edge_caddy    │  ← он и сейчас там; добавляем admin API
                  │  (Caddy 2)      │     на :2019 внутри сети edge
                  └───┬──────────┬──┘
     panel.домен ─────┘          └───── сайты пользователя
                  ┌───▼─────────────────┐
                  │  edgedeck           │  бэкенд + встроенный UI
                  │  :4000 (не публикуем)│  ─ пишет ~/edge/routes.yaml + sites/*.caddy
                  └───┬──────────────┬──┘  ─ POST /load в admin API Caddy
                      │              │     ─ SQLite: сессия, аудит, кэш проверок
        ┌─────────────▼──┐    ┌──────▼───────────────┐
        │ edgedeck-agent │    │ /host/proc  (ro)     │
        │ docker: чтение │    │ порты вне докера     │
        │ + connect edge │    │ (§2.5)               │
        └───────┬────────┘    └──────────────────────┘
                │
         /var/run/docker.sock (ro)
```

**Почему свой `edgedeck-agent`, а не `tecnativa/docker-socket-proxy`.** Готовый прокси
даёт права секциями и методами: чтобы разрешить `POST /networks/*/connect` (нужно для
§2.3), придётся включить `POST=1`, а это откроет и `POST /containers/create`,
`/containers/{id}/start` — то есть запуск чего угодно от имени панели. Пользователь
согласился на «читать docker.sock через прокси-фильтр» и «подключать контейнеры к сети
edge» — ровно это и не больше даёт свой сайдкар на ~150 строк с белым списком:

```
GET  /containers/json, /containers/{id}/json, /networks, /networks/{id}, /info, /version
POST /networks/edge/connect        ← только сеть edge, только контейнер, который существует
POST /networks/edge/disconnect
всё остальное → 403
```

`docker.sock` монтируется **только** в агент, режимом `:ro`, и агент не умеет `exec`.

**Права панели, сведённые в таблицу:**

| действие | можно | как |
|---|---|---|
| читать список контейнеров, сетей, портов | да | агент |
| подключать/отключать контейнер к сети `edge` | да | агент, белый список |
| писать в `~/edge/` (routes.yaml, sites/, www/) | да | том rw |
| перезагружать Caddy | да | admin API, без docker exec |
| запускать/останавливать/удалять контейнеры | **нет** | — |
| править чужие compose-файлы | **нет** | показывает кусок yaml для копирования |
| менять ufw / DOCKER-USER / iptables | **нет** | показывает готовую команду (§2.16) |
| менять DNS у регистратора | **нет** | только проверяет A-запись (§2.8) |

DNS у доменов сейчас на Hostinger (`*.dns-parking.com`) и thehost.com.ua. У Hostinger
API есть, но автоматическое управление DNS в первую версию не берём: цена ошибки высокая,
а выигрыш — одна ручная операция на домен.

## 5. Источник истины и как применяется изменение

### 5.1. Один файл, который читает и человек, и панель

```
~/edge/
  routes.yaml        ← ИСТОЧНИК ИСТИНЫ. Правит панель, можно править руками.
  sites/*.caddy      ← генерируется из routes.yaml. В шапке: «СГЕНЕРИРОВАНО, не править»
  snippets/*.caddy   ← общие блоки (common, hsts, cors, internal_only) — как сейчас
  www/<домен>/       ← статика
  logs/              ← логи Caddy

~/edgedeck/data/
  snapshots/<время>/ ← снимок перед каждым применением: routes.yaml + sites/
```

Почему не хранить всё в базе: панель тогда становится единственным способом узнать, что
происходит на сервере (§2.19), а Caddyfile не разбирается обратно в структуру без
боли. Почему не редактировать `sites/*.caddy` напрямую: чтобы галочка «WebSocket» в UI
не превращалась в текстовый парсер с угадыванием.

`routes.yaml` выглядит так — читается без документации:

```yaml
routes:
  - domain: tgdesk.tech
    aliases: [www.tgdesk.tech]        # редирект на основной
    path: /
    type: proxy
    target: {kind: container, name: twcrm-frontend, port: 80}
    websocket: true
    max_upload: 32MB
    headers: {hsts: false, security_defaults: true}

  - domain: bogun.site
    path: /logs/
    type: proxy
    target: {kind: container, name: dozzle, port: 8080}
    websocket: true
    timeout: 1h
    auth: {kind: forward, url: "http://jarvis:4000/api/authcheck"}   # §2.10
```

### 5.2. Применение — транзакция с откатом

Изменение никогда не применяется «просто так». Порядок фиксированный (реализовано
в `internal/apply`):

```
1. проверка формы        домен валиден? путь не занят другим маршрутом?
                         цель указана? порт в диапазоне?
2. генерация в памяти    routes.yaml → sites/*.caddy, ничего не записано
3. валидация             POST /adapt — ДО записи на диск: строки import
                         подставляются содержимым файлов, поэтому конфиг можно
                         проверить целиком, не тронув прод
4. эталон                как отвечают ВСЕ домены прямо сейчас
5. снимок                копия routes.yaml и sites/ в data/snapshots/<время>
6. запись                файлы на диск, владелец — как у ~/edge
7. применение            POST /load — Caddy подхватывает без разрыва соединений
8. контроль              те же домены опрашиваются снова; если разошлось —
                         пауза 6 секунд и ещё раз (сертификат нового домена
                         выпускается не мгновенно)
9. авто-откат            стало хуже → вернуть снимок, применить его и сказать,
                         что именно сломалось
```

Проверка доменов идёт **через сам Caddy**: TLS-соединение к контейнеру прокси с
нужным SNI и обычный GET. То есть тем же путём, которым пойдёт браузер, — а не
«конфиг синтаксически верен, значит всё хорошо».

Порядок отличается от первоначального замысла в одном: валидация переехала
**до** записи. Так лучше — сломанный конфиг вообще не попадает на диск.

Пункт 7 — прямое следствие §2.1 и §2.12: ломается обычно не то, что менял.
Панель до изменения снимает эталон по всем маршрутам, после — сравнивает.

### 5.3. Ручные правки не теряются

Панель на старте и раз в минуту сверяет: `routes.yaml` → сгенерированные файлы совпадают
с тем, что на диске? Если кто-то правил `sites/*.caddy` руками (по SSH, в аварии) —
панель не перетирает молча. Показывает: «файл X изменён вне панели, вот diff» и даёт
выбор: принять как есть (пометить маршрут «управляется руками», больше не генерировать)
или перегенерировать. Маршруты, помеченные «руками», панель показывает, но не трогает.

## 6. Как панель выбирает цель «по умному»

Это то, что отличает панель от текстового редактора.

### 6.1. Дискавери — что вообще есть на сервере

Панель постоянно держит актуальный список кандидатов из трёх источников:

**Контейнеры** (через агент): имя, образ, сети, `EXPOSE`-порты, опубликованные порты,
compose-проект и его каталог, метки, состояние. Для каждого — вычисленный вывод:
* в сети `edge` → готов, адрес `имя:порт`;
* в другой сети → «нужно подключить к edge» + кнопка;
* сети нет (host/none) → «через host.docker.internal», с оговоркой §2.6;
* несколько `EXPOSE`-портов → панель предлагает угадать (см. §6.3).

**Порты хоста** (через `/host/proc/1/net/tcp{,6}` + `udp`, инод → pid → cmdline):
номер, процесс, интерфейс. Так находятся `pufferpanel`, `java`, `node_exporter` (§2.5).
`/proc` монтируется только на чтение, как у node_exporter.

**Папки** в `~/edge/www/` — готовая статика.

### 6.2. Предполётная проверка — до записи в конфиг

Панель делает пробный запрос **из сети `edge`** (то есть точно оттуда, откуда потом
пойдёт Caddy) и показывает результат человеческим языком:

| что проверяем | что говорим пользователю |
|---|---|
| TCP-соединение | «порт открыт» / «соединение отклонено — контейнер жив, но порт не тот» / «нет маршрута — цель в другой сети» |
| HTTP-ответ | «отвечает 200» / «отвечает 302 на https — цель сама редиректит, будет петля, поставь `redirect: false`» |
| ответ на `Host: домен` | «цель уважает Host» / «цель отдаёт другой сайт без правильного Host» |
| заголовки цели | «цель уже ставит CSP / HSTS» → влияет на тумблеры (§2.11) |
| WebSocket | пробный `Upgrade` → «поддерживает, включаю долгие соединения» |
| A-запись домена | «домен смотрит сюда» / «смотрит на 1.2.3.4 — TLS не выпустится» (§2.8) |
| порт 80 снаружи | «ACME-проверка пройдёт» |

Ничего из этого не требует от пользователя знать слова «апстрим» и «резолвер».

### 6.3. Догадки, которые панель озвучивает, а не применяет молча

* один `EXPOSE`-порт → он и есть цель;
* несколько → приоритет 80, 8080, 3000, 4000, 5000, 8000, и тот, который отвечает
  HTTP при проверке;
* образ известного вида (`nginx`, `caddy`, `traefik`, `*-frontend`) → 80;
* имя контейнера совпало с частью домена (`twcrm-frontend` ↔ `tgdesk.tech` — не совпало,
  а вот `apiary-web` ↔ `bots.bogun.site` — по compose-проекту) → предлагаем первым;
* контейнер уже упомянут в другом маршруте → показываем, где, чтобы не задублировать.

Каждая догадка в UI подписана: «выбрал порт 80, потому что он единственный отвечает
HTTP». Пользователь может переопределить в один клик.

## 7. Сертификаты

Всё делает Caddy, панель — витрина и сторож.

* Список: домен, срок, дней осталось, кем выпущен, последняя попытка продления.
* Цвета: < 21 дня — жёлтый (Caddy обновляет за 30 дней, значит что-то не сработало),
  < 7 дней — красный.
* Явная плашка про лимит Let's Encrypt и про том `caddy_data`, который нельзя удалять.
* Кнопка «выпустить сейчас» существует, но неактивна, пока не прошла проверка A-записи
  (§2.8), и с счётчиком «попыток на этой неделе: 2 из 5».
* **`on-demand TLS` нужен с первого этапа** — без него не работает главный сценарий §9.0
  (добавил A-запись, сразу открыл `https://новый-домен` и попал в панель). Сертификат
  выпускается на первый запрос, разрешение спрашивается у панели:

  ```
  Caddy → GET http://edgedeck:4000/internal/tls-ask?domain=example.com
        ← 200 (можно)  /  403 (нельзя)
  ```

  Панель отвечает 200 только если: (а) домен резолвится и его A-запись = внешний IP этого
  сервера; (б) за последний час выдано меньше 10 разрешений на новые домены; (в) домен не
  в чёрном списке. Без такой проверки любой, кто направит свой домен на наш IP, будет
  жечь наши лимиты Let's Encrypt (§2.8). Ответы кэшируются на 5 минут, отказы — на час.
* Заход **по IP** сертификата не получит: для IP-адреса Let's Encrypt их не выдаёт.
  Поэтому `https://150.136.40.217` отдаст самоподписанный сертификат Caddy (`tls internal`)
  — браузер покажет предупреждение, это нормально и ожидаемо. Пароль по такому каналу
  всё равно защищён шифрованием, просто без подтверждённой подлинности. В панели на этот
  случай висит подсказка: «зайдите по домену, чтобы предупреждение исчезло».

## 8. Порты и три слоя фильтрации

Отдельный экран, потому что вопрос «а это видно из интернета?» на старых серверах не
имел быстрого ответа (§2.16). **Сделано на этапе 2.**

Читать `iptables` можно только с `CAP_NET_ADMIN` и в сетевом пространстве хоста —
прав, которых панели давать нельзя. Поэтому они вынесены в отдельный контейнер
`edgedeck-firewall`, который:

* умеет ровно три чтения (`DOCKER-USER`, `INPUT`, файл `user.rules`) и ни одной записи;
* **никуда не слушает** — нет порта, нет и способа его о чём-то попросить;
* раз в 30 секунд кладёт снимок в файл, а панель монтирует этот каталог только на чтение.

Худшее, что даёт этот канал взломанной панели — устаревший дамп правил.

Вывод для хостового порта делается **обходом цепочки INPUT по порядку**, а не
одним флагом «работает ли ufw»: на oracle-3 SSH доступен именно потому, что
Oracle разрешает 22 явным правилом выше своего `REJECT`. Первое совпавшее правило
и решает; безусловный запрет закрывает всё ниже; переход в ufw-цепочку передаёт
решение правилам ufw. На эту логику написаны тесты с настоящими выгрузками с
серверов 1 и 3 — они и поймали две ошибки в ней.

Для каждого порта панель собирает:

```
порт 3341/tcp   слушает: docker-proxy → контейнер tgshop_v2_mysql (MySQL)
  интерфейс:    0.0.0.0  (все)
  DOCKER-USER:  правил нет
  ufw:          правила нет
  Oracle SL:    неизвестно (панель туда не ходит)
  ─────────────────────────────────────────────
  вывод:        🔴 ВИДНО ИЗ ИНТЕРНЕТА. База данных.
  что сделать:  sudo /opt/docker-acl/apply.sh  после строки:
                echo "3341  132.145.132.80/32" >> /opt/docker-acl/ports.conf
```

Правила панель не применяет — пользователь так решил. Она формирует точную команду с
учётом того, какой слой в данном случае вообще работает (на s3 — только `DOCKER-USER`
для docker-портов, ufw бесполезен, §2.6).

Отдельный флаг для того, что найдено на s1: если порт держит база данных, админка,
docker-socket-proxy или Portainer-агент, и правил нет — это красный уровень, а не
информация.

## 9. Интерфейс

Пользователь попросил «просто по паролю и красивый приветственный экран с уже списком
развёрнутых доменов». Отсюда четыре экрана и один визард.

### 9.0. Панель — это обработчик по умолчанию

Главное решение по доступу, и оно же — главный сценарий работы:

```
любой домен без маршрута   ─┐
любой поддомен без маршрута ├──→  ПАНЕЛЬ  (сертификат выпускается на месте, §7)
заход напрямую по IP       ─┘     (по IP — самоподписанный, с предупреждением браузера)

домен, у которого есть маршрут  ──→  сайт
```

То есть цикл добавления сайта такой: направил A-запись на сервер → открыл этот домен в
браузере → **попал в панель, уже залогиненный или с формой пароля** → на приветственном
экране домен уже виден в списке «пришли, но не настроены» → нажал «настроить» → выбрал
цель → применил → обновил страницу и там уже сайт.

Никакого выделенного домена для панели не нужно и никакого белого списка IP нет: заходим
откуда угодно, единственная защита — пароль (§10).

Два следствия, которые надо держать в голове:

* **Панель светится на каждом ненастроенном домене.** Это осознанный компромисс за
  удобство. Поэтому форма входа не должна выдавать ничего, кроме себя: ни имени сервера,
  ни списка доменов, ни версии — всё это появляется только после входа. (В отличие от
  §9.2, где на приветственном экране видно всё.)
* **Если панель лежит, ненастроенные домены отдают ошибку.** Настроенные сайты при этом
  живы — они обслуживаются Caddy напрямую и панель им не нужна ни для чего.

### 9.1. Первая страница: витрина сайтов, потом пароль

Решение пользователя: «на главной прям перед паролем — обозреватель уже зареганных
сайтов, а для управления и добавления новых уже пароль и админка».

```
                    ┌───────────────────────────────────┐
                    │            EdgeDeck               │
                    │       сайты этого сервера         │
                    ├───────────────────────────────────┤
                    │ ● test.bogun.site      сайт     → │
                    │ ● s3.bogun.site        статика  → │
                    │ ○ shop.example.com     сайт     → │
                    ├───────────────────────────────────┤
                    │          [ Управление ]           │
                    └───────────────────────────────────┘
```

Витрина открыта всем, потому что скрывать там нечего: имена настроенных доменов и так
публичны — они есть в DNS и в логах Certificate Transparency, по которым любой домен с
сертификатом виден и без нас. Точка (●/○) — отвечает ли цель.

А вот что до входа **не** отдаётся, и это ровно та граница, которую нельзя размывать:

| наружу | под паролём |
|---|---|
| имена настроенных доменов | имена контейнеров и порты — карта внутренностей |
| «отвечает / не отвечает» | домены из «пришли, но не настроены» — планы и опечатки |
| — | имя сервера, адрес, версия, нагрузка |
| — | порты, сертификаты, журнал действий, любые изменения |

Кнопка «Управление» раскрывает форму пароля. Пароль один (argon2id в файле конфига),
сессия — httpOnly-кука на 30 дней, 5 попыток в 15 минут с одного адреса, потом пауза.
Ответ на неверный пароль скупой и одинаковый. TOTP — опция в настройках, выключена.

## 10. Безопасность

* Порт панели **не публикуется** на хосте: снаружи в неё можно попасть только через Caddy
  (то есть по 80/443), никакого `4000` в интернете нет.
* Доступ **откуда угодно**, по любому ненастроенному домену или по IP (§9.0). Белого списка
  IP по умолчанию нет — заходим и с телефона. Соответственно вся защита — на пароле и
  ограничении попыток, и это принято сознательно.
* Пароль: argon2id, соль в файле, файл 600. Смена пароля — в панели.
* Сессия: httpOnly + Secure + SameSite=Lax, срок 30 дней, список активных сессий с
  кнопкой «выйти везде».
* Ограничение попыток входа, лог всех попыток.
* Панель не умеет: запускать контейнеры, читать чужие тома, выполнять команды, менять
  фаервол. Максимум ущерба при захвате — переписанные маршруты, которые видно в git и
  откатываются одной командой.
* Опционально (по желанию): дополнительный ACL по IP через `internal_only`-сниппет,
  который уже есть на s3. Не по умолчанию — пользователь хочет заходить с телефона.
* Свои логи: доступ и действия отдельно, ротация как у Caddy (10 МБ × 5).

## 11. Стек и почему такой

| | выбор | почему |
|---|---|---|
| Бэкенд | **Go 1.23**, один статический бинарник | 2 ядра на s3 и цель «до 64 МБ»: Node с зависимостями съест больше, а тут образ ~25 МБ и нет рантайма. Плюс ARM-сборка без танцев |
| Агент докера | Go, тот же бинарник, режим `--agent` | не тащить второй язык ради 150 строк |
| Фронтенд | React + Vite + Tailwind, вшит в бинарник (`embed.FS`) | привычный стек проектов; отдаётся тем же процессом, отдельного nginx не нужно |
| Хранилище | файлы (`routes.yaml`) + SQLite для сессий/аудита/кэша проверок | §5.1 |
| Прокси | **существующий Caddy**, управление через admin API | ничего не переписываем; `bin/newsite`/`bin/reload` остаются рабочими |
| L4 (2-й этап) | своя сборка `xcaddy` + `mholt/caddy-l4` | Dockerfile закладываем сразу, чтобы потом не менять образ на живом сервере |

Что придётся поменять в текущем `~/edge`, минимально:

1. `admin localhost:2019` → `admin :2019` в `Caddyfile` (чтобы панель дошла по сети
   `edge`; порт не публикуется, снаружи недостижим).
2. `sites/` и `www/` смонтировать панели на запись.
3. `extra_hosts: ["host.docker.internal:host-gateway"]` у Caddy — для цели «процесс на
   хосте» (с оговоркой §2.6).

## 11.1. Сборка и доставка

Разработка ведётся в приватном репозитории **`vladbogun1/edgedeck`** на GitHub, и это
единственное место, где собираются образы. Локально на машине ничего собирать не нужно
(и Go локально не установлен — проверка компиляции идёт через `docker run golang`).

```
D:\CLOUDE\edgedeck  ──git push──→  github.com/vladbogun1/edgedeck (private)
                                            │
                                     GitHub Actions
                                     ├─ go vet + тесты
                                     ├─ сборка фронта (vite) → вшивается в бинарник
                                     └─ docker buildx: linux/arm64 + linux/amd64
                                            │
                                     ghcr.io/vladbogun1/edgedeck:<тег>
                                            │
                          сервер: ~/edgedeck  docker compose pull && up -d
```

* **Платформа обязательно `linux/arm64`** — все три сервера на aarch64 (Ampere A1).
  amd64 собираем заодно, чтобы можно было погонять локально.
* Теги: `main` (последний коммит основной ветки), `sha-<короткий хеш>` (на что откатываться),
  `vX.Y.Z` при релизе. На сервере в compose стоит **конкретный тег**, а не `latest`:
  обновление — это осознанная правка одной строки, а не «оно само подтянулось».
* На сервере лежит только `~/edgedeck/docker-compose.yml` + `.env` + данные. Исходников на
  сервере нет — так же, как у apiary (`ghcr.io/vladbogun1/apiary-*`), который уже так живёт.
* Пакет в GHCR приватный, поэтому серверу нужен `docker login ghcr.io` с токеном, у
  которого есть только `read:packages`. Токен кладём в `~/.docker/config.json` один раз;
  в репозиторий он не попадает.
* Каталоги на сервере: `~/edgedeck/` (панель) и существующий `~/edge/` (Caddy + конфиги),
  который панель монтирует внутрь себя на запись.

## 13. Чего панель НЕ делает

* Не деплоит приложения и не собирает образы — это не Portainer и не CI.
* Не запускает и не останавливает контейнеры.
* Не правит чужие `docker-compose.yml` — только показывает готовый фрагмент.
* Не управляет DNS у регистратора — только проверяет A-запись.
* Не меняет фаервол — только формулирует точную команду.
* Не управляет другими серверами — на каждом своя копия.
* Не собирает статистику посещений (это работа логов и мониторинга, которые уже есть).
