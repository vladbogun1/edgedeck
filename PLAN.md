## P0 — безопасность и честность (из реальных инцидентов)

### P0-1. Сети проектов вместо общей `edge`

**Что случилось.** Сеть `edge` стала общей для всех проектов сервера. Docker Compose
регистрирует в каждой сети не только имя контейнера, но и **короткое имя сервиса**. На s3
10.10 в `edge` были: `admin`, `app` (exfiltration), по два контейнера с именами
`gateway-admin` и `gateway-site` (демо магазина и магазин движка), а ещё `caddy`, `panel`,
`agent`. nginx нового магазина ходил к своей админке по имени `admin` и попадал в чужой
проект → 502 → автооткат. Хуже 502 был бы «успешный» ответ: запрос с cookie одного проекта
уходит в другой.

**Как надо.** Проекты в `edge` не кладём. Caddy сам подключается к сети проекта — так уже
устроен s1 (`root_website_hubnet`, `apiary_net`, `maxsolch-v2_tgshop`, …). Короткие имена
остаются внутри своей сети и столкнуться не могут.

**Сделать.**
- Агент: новая операция «подключить `edge_caddy` к сети X» (и отключить). Белый список
  агента расширяется ровно на неё; подключать чужие контейнеры к чужим сетям он не умеет.
- Цель маршрута получает поле `network:` (по умолчанию — первая сеть контейнера, кроме
  `bridge`). Перед применением панель проверяет, что Caddy в этой сети, и при
  необходимости подключает. Самолечение (reconcile) держит подключение Caddy к нужным
  сетям, как сейчас держит контейнеры в `edge`.
- Экран «Цели»: кнопка «подключить к сети edge» заменяется на «пустить Caddy в сеть
  проекта». Подсказка про `networks: edge: external` в compose — убрать, вместо неё —
  «ничего прописывать не нужно».
- **Детектор коллизий**: агент отдаёт псевдонимы контейнеров в каждой сети. Если одно
  короткое имя в одной сети принадлежит контейнерам разных compose-проектов — красное
  предупреждение на «Доменах» и в «Целях» с объяснением и кнопкой «увести проект из
  edge» (Caddy подключается к сети проекта, контейнер отключается от `edge`, маршрут
  перепроверяется пробой; при ошибке — назад).
- Миграция существующего: s3 (exfiltration, demo, shop-*, ai-playground, obs-overlay,
  demo-test-web) и s1 (`twcrm-frontend` в `edge`). По одному проекту, с пробой домена до и
  после.
- Скилл `edgedeck`: правило «проекты не подключать к edge, Caddy сам придёт в сеть
  проекта».

**Готово, когда** в `edge` остаются только `edge_caddy`, `edgedeck`, `edgedeck-agent`, а
детектор на всех трёх серверах молчит.

### P0-2. «Последнее применённое» состояние

**Что случилось.** Агент правит `routes.yaml` руками и зовёт `--apply`. Снимок делается
*после* правки — в нём уже новые маршруты. Автооткат возвращает файлы сайтов, а
`routes.yaml` остаётся с изменениями: файл описывает то, чего на сервере нет, и следующее
применение по любому поводу молча выкатит их (или, при смене доменов, молча снимет старые).

**Сделать.**
- `data/applied/routes.yaml` — копия конфига, который **успешно** применён последним.
  Пишется только после контроля без регрессий.
- Снимок берёт `routes.yaml` из `applied`, а не с диска. Откат (авто и ручной) возвращает
  и `routes.yaml`; изменённый файл сохраняется рядом как `routes.yaml.rejected-<время>`,
  чтобы правку не потерять.
- Расхождение `routes.yaml` ↔ `applied` видно везде: `--plan` печатает «в файле есть
  неприменённые изменения: +a, −b, ~c»; в панели — жёлтая плашка «Есть неприменённые
  правки routes.yaml» с кнопками «Применить» / «Вернуть как было».
- Расхождение «сгенерированный файл ≠ то, что выдал бы генератор» (как было с ручной
  правкой `app.demo.chisetup.com.ua` 09.10) — тоже плашка, с diff.

**Готово, когда** после любого автоотката `routes.yaml` совпадает с работающими сайтами, а
ручная правка без применения видна в панели.

### P0-3. Журнал и Telegram для применений по SSH

**Что случилось.** `--apply` идёт мимо журнала и уведомлений: 10.10 агент сделал три
применения и автооткат на s3 — в «Истории» пусто, в Telegram тишина.

**Сделать.**
- CLI пишет в тот же `audit.jsonl` (`apply`, `apply_failed`, `rollback_auto`) и шлёт те же
  сообщения в Telegram, что и кнопка панели.
- `--actor <кто>` (по умолчанию `ssh`): агенты подписываются, например
  `--actor agent:commerce-engine`. В «Истории» видно, кто менял.
- «История» показывает и снимки, сделанные по SSH, с причиной (`--reason`).

### P0-4. Владелец маршрута и `routes sync`

**Что случилось.** `commerce-engine` управляет своими маршрутами скриптом, который правит
`routes.yaml` регулярками и узнаёт «свои» маршруты по фразе в `comment`. Это работает, но
хрупко: другое форматирование файла — и скрипт не увидит домен; переписанный комментарий —
и маршрут осиротеет или попадёт под удаление.

**Сделать.**
- Поле `owner:` у маршрута (например `commerce-engine/chisetup`). Панель показывает его
  меткой и не даёт править такой маршрут в визарде без подтверждения.
- `edgedeck routes sync --owner X --file desired.json [--actor …] [--reason …]` —
  желаемое состояние маршрутов владельца: добавить недостающие, обновить изменённые,
  удалить лишние **только с этим owner**. Домен, занятый маршрутом без owner или с другим
  owner, — отказ с понятной ошибкой. Одна транзакция, откат по P0-2.
- `edgedeck routes list --json` — для скриптов; `--plan --json` — машиночитаемый план.
- Коды выхода: 0 — применено/нечего делать, 2 — конфликт владельца, 3 — Caddy не принял,
  4 — откатилось.
- Перевести `commerce-engine/deploy/server/edge-routes.py` на `sync` (в его репозитории),
  существующие маршруты движка разметить `owner` по их текущей пометке в `comment`.
- Скилл `edgedeck`: раздел «автоматизация» с `sync` вместо правки YAML.

## P1 — флоу, которых не хватает в ежедневной работе

### P1-1. Стек как сущность

Сейчас стек — только картинка (группировка по зоне). Повседневные операции делаются по
одному домену, хотя мыслятся стеком: «подними магазин на app./admin./корне», «переедь
магазином на новый домен».

- **Создать стек из compose-проекта.** Выбрал проект → панель находит сервисы с HTTP
  (проба портов), предлагает раскладку «корень → site, app. → miniapp, admin. → admin»,
  показывает DNS-проверку всех имён сразу, применяет одной транзакцией, Caddy входит в
  сеть проекта (P0-1).
- **Переезд стека на другой домен.** Новые имена получают маршруты, старые — не удаляются, а
  становятся 301 на новые с сохранением пути (тип `redirect`) с пометкой «снять после
  <дата>»; напоминание в Telegram в эту дату. Сейчас агент просто снимает старые адреса — и
  ссылки на них ломаются.
- **Действия над стеком целиком:** включить/выключить сжатие, режим обслуживания (P1-5),
  удалить стек.

### P1-2. Логи и история доступности

Caddy уже пишет JSON-журнал каждого сайта (`/var/log/caddy/<домен>.log`), а сторож раз в
минуту проверяет сайты — но ни то, ни другое нельзя посмотреть.

- Карточка сайта: запросы/ошибки за сутки (2xx/3xx/4xx/5xx), медиана времени ответа,
  последние 5xx с путём и временем, топ путей и адресов. Чтение файлов логов (том уже
  смонтирован Caddy, панели — только чтение).
- Живой хвост журнала сайта (SSE) — для отладки 502 прямо из панели.
- История доступности: каждое «упал/поднялся» сторожа пишется в `data/uptime.jsonl`;
  полоска доступности за 30 дней на витрине и в панели, список инцидентов.

### P1-3. Обновление панели без ручного scp

Сейчас: `gh run download` → scp на три сервера → `docker load` → `up -d`. Каждый раз руками.

- Варианты (выбрать один):
  - fine-grained токен только на чтение пакетов GHCR в `.env` сервера → `docker compose
    pull` работает, и панель может обновиться сама по кнопке «Обновить» (через агента:
    pull + пересоздание своего контейнера).
  - или скрипт `deploy/update.sh` локально: один вызов обновляет все три сервера по SSH
    с откатом при неудачном healthcheck.
- В «Настройках»: текущая версия, есть ли новее (по GitHub), кнопка/команда обновления,
  история версий и откат на `rollback`-образ.

### P1-4. Новый сервер одной командой

`install.sh` требует готовый `~/edge` с Caddy, а его сейчас копируют руками из
`infra\oracle\server-3`.

- `install.sh --with-edge`: поднимает `~/edge` (Caddyfile, сниппеты, `bin/`, compose
  Caddy, сеть, том), затем панель. Telegram-токен и чат — параметрами, без вывода в лог.
- Проверка в конце: заход по IP, выпуск сертификата на тестовый поддомен, сообщение
  «сервер подключён» в Telegram.
- Обновление скилла и `_kb/servers.md` — в инструкции по завершению.

### P1-5. Режим обслуживания

Во время выкатки сайт отдаёт 502, и сторож шлёт тревогу. Нужно: «сайт на обслуживании» —
страница «скоро вернёмся» с кодом 503 и `Retry-After`, тревоги по этому сайту молчат.
Включается кнопкой, из CLI (`edgedeck maint on <домен|стек> [--for 30m]`) и
автоматически снимается по таймеру.

### P1-6. DNS-подсказки

- При добавлении домена: куда сейчас смотрит A-запись; если на **другой из своих
  серверов** — так и сказать («это s1») вместо «смотрит не сюда».
- Распознавать wildcard-записи и Cloudflare-прокси (оранжевое облако): там
  `tls-ask` по IP не сойдётся, нужна подсказка.
- Перед удалением маршрута: «домен всё ещё смотрит сюда — после удаления он попадёт в
  панель как ненастроенный».

## P2 — удобства

- Поиск/командная палитра (`Ctrl+K`): домен, контейнер, порт → переход.
- История `routes.yaml` в git: каждое применение — коммит в локальный репозиторий
  `~/edge/.git` (diff «кто что менял» и откат на любую точку).
- Уведомления: тихие часы, отключение тревог по сайту, ежедневная сводка вместо потока.
- Мобильная установка (PWA) для быстрого взгляда со смартфона.
- `edgedeck doctor`: одна команда проверяет всё — сеть Caddy, коллизии имён, расхождения,
  сертификаты, фаервол-снимок, Telegram — и печатает, что чинить.
- Экран «Порты»: генерировать готовую строку для `/opt/docker-acl/ports.conf`, а не
  только словесный совет.
- e2e-тесты интерфейса на `vite.mock.config.ts` (Playwright) в CI.

## Вопросы к пользователю (меняют границы из DESIGN §13)

- **Q-1. Общий вид всех серверов.** Сейчас «у каждого сервера своя панель» (решение
  19.08). На практике работа идёт сразу на трёх. Вариант: витрина/обзор, которая читает
  публичные API других панелей (только чтение, по токену) и показывает все стеки, статусы
  и сертификаты в одном месте; управление остаётся на своём сервере. Нужно?
- **Q-2. Вход для приватных сервисов через EdgeDeck.** JARVIS, dozzle, ai-playground,
  Portainer — у каждого свой вход или его нет. EdgeDeck уже умеет вход кодом в Telegram;
  может стать `forward_auth` для любого маршрута (`auth: edgedeck`) — один вход на все
  личные инструменты. Это расширение роли панели (из маршрутизатора — в шлюз доступа).
  Делаем?
- **Q-3. L4 (TCP/UDP, SNI на 443 у s2).** Этап 3 из DESIGN так и не начат. Актуально
  (Minecraft, xray), или вычёркиваем?
